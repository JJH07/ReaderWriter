# 검증 안내

## 자동 검증

[CI 실행 기록](https://github.com/JJH07/ReaderWriter/actions/workflows/ci.yml)에서 검토할 커밋을 선택하세요. 각 실행에는 다음 세 작업이 있습니다.

| 작업 | 검사 |
| --- | --- |
| GCC / `make test` | C11, `-Wall -Wextra -Wpedantic -Werror`, 통합 테스트 |
| Clang / `make test` | 다른 컴파일러의 동일 경고 검사와 통합 테스트 |
| GCC / `make sanitize` | AddressSanitizer·UndefinedBehaviorSanitizer 및 통합 테스트 |

통합 테스트 25개는 테스트마다 별도 임시 디렉터리, 소켓, 프로세스를 생성합니다. 실제 편집기 UI 대신 파일을 수정하는 자동 편집기 fixture를 사용합니다.

검증 범위:

- 인자 부족, 잘못된 모드·큐 크기·시간 제한, 과도하게 긴 확인 입력
- 읽기 전용 실행과 수정 시간 표시, 취소 시 원본 보존
- 처음 실행 시 디렉터리 권한, 기본 소켓과 별도 로그 디렉터리
- 편집·내용 비교·크기·diff·로그 사본, 수정 시간을 유지한 내용 변경
- 편집기 실행 실패·스냅샷 실패 뒤 다음 편집 진행
- 잘못된 파일·잘못된 패킷, 요청 폭주 시 패킷 경계와 접수 순서
- 큐 포화, 대기 시간 초과, 대기자·활성 연결 해제
- 8개 편집 클라이언트의 동시 실행에서 편집 구간 중첩 여부
- 래퍼 강제 종료 후에도 실행 중인 편집기의 연결 수명 유지
- 중복 데몬 차단, 기존 일반 파일 보호, 활성 편집 없는 비정상 종료 후 재시작
- 정상 종료 시 현재 편집 대기, 백그라운드 시작·종료

로컬 재현:

```sh
make clean
make CC=gcc test
make clean
make CC=clang test
make CC=gcc sanitize
```

Sanitizer 오류가 발생하면 CI가 실패합니다. 테스트가 정리하는 서버 프로세스의 표준 오류도 ASan·LSan·UBSan 진단 여부를 확인합니다. 강제로 종료하는 테스트에서는 정상 종료 시 실행되는 누수 검사를 기대하지 않습니다.

## 직접 확인하기

1. `make` 후 테스트용 파일을 만들고 `./ssu_ofm 파일 -f -t -id -n 1`을 실행합니다.
2. 두 번째 터미널에서 `./ssu_vim 파일 -w -t -s -d`로 편집기를 엽니다.
3. 세 번째 터미널에서 같은 명령을 실행하면 첫 편집기가 끝날 때까지 대기합니다. 30초 이상 기다려야 한다면 `--timeout 120`을 지정합니다.
4. 첫 편집기를 종료하면 두 번째 편집기가 열리는지 확인합니다. 크기·diff는 자신의 편집 결과를 기준으로 출력됩니다.
5. 다른 파일에 `./ssu_vim 다른파일 -rw`를 실행하고 `no`를 입력하면 원본이 유지되는지 확인합니다.
6. 데몬에 SIGTERM을 보내면 대기자는 오류로 종료되고 현재 편집은 끝날 때까지 기다리는지 확인합니다.

현재 자동 테스트는 Linux 프로세스 동작과 프로토콜 검증입니다. 실제 Vim·Nano의 터미널 화면, 강제 데몬 종료 후 활성 편집 복구, 외부 프로그램과의 파일 잠금은 검증하지 않습니다.
